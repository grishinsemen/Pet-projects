# Системный анализ

Здесь лежат проекты, в которых я описываю систему так, как это делает системный аналитик: требования, процессы, данные и интеграции. Кода почти нет, главное в документах.

## Что есть в каждом проекте

| Артефакт | Файл | Зачем |
|---|---|---|
| Карточка проекта | `README.md` | Цель, границы, принятые решения и почему |
| Требования | `docs/01-requirements.md` | Что система должна делать и в каких рамках |
| Пользовательские истории | `docs/02-user-stories.md` | Сценарии глазами пользователя с критериями приёмки |
| Бизнес-процесс | `docs/03-business-process.md` | Как работает процесс, кто за что отвечает |
| Модель данных | `docs/04-data-model.md` | Сущности, связи, атрибуты |
| Интеграция | `docs/05-integration.md` | Как системы обмениваются данными и что при сбоях |
| Описание API | `api/openapi.yaml` | Контракт в формате OpenAPI |

Диаграммы написаны на Mermaid, GitHub рисует их прямо в README. Для полноценного BPMN кладите файл `.bpmn` из Camunda Modeler рядом с описанием.

## Как начать новый проект

1. Скопируйте папку `_template` и назовите её `NN-название`, например `01-запись-к-врачу`.
2. Заполните `README.md` проекта и первые два документа. Остальные добавляйте по мере необходимости, ненужные удаляйте.
3. Все `TODO` и подсказки в угловых скобках замените своим текстом или удалите.
4. Добавьте проект в таблицу в корневом README.

## Правила

- Один проект описывает одну систему. Лучше один проработанный проект, чем пять поверхностных.
- В карточке проекта записывайте, какие решения приняты и почему. Это то, о чём спрашивают на собеседовании.
- Открытые вопросы не прячьте, а перечисляйте: так видно, что вы понимаете границы знаний.
